뼈대만 커밋됨. 이 문서는 **방향과 우선순위**를 적는다. 수치는 `GAME_RULES.md`, 인프라

## 3. 클라우드 설계 공고화 — 최우선

지금 구성은 "한 대로 돌아가는 최소 구성"으로는 잘 되어 있다. 이제 바뀐 것은 **DB에
지켜야 할 것이 생겼다**는 점이다. V1의 DB는 랭킹뿐이었지만 지금은 플레이어의 돈, 창고,
의뢰 진행이 들어 있고, 11/01에는 처음으로 **운영 DB를 대량으로 지우는 작업(시즌 와이프)**이
자동으로 돈다. 공고화의 목표는 세 가지다.

1. **잃지 않는다** — 백업, 복원 훈련, 와이프 전 스냅샷
2. **다시 만들 수 있다** — 콘솔에서 손으로 만든 인프라를 코드로(IaC)
3. **보인다** — 서버 안(틱 시간, 접속자)을 지표와 경보로

`CLAUDE.md` §10의 원칙은 그대로다. ALB, Redis, 두 번째 서버는 아래 C-트리거가 오기 전에는
넣지 않는다. 공고화는 서비스를 늘리는 일이 아니라 **지금 있는 한 대를 단단하게** 하는 일이다.

### 3.1 위험 목록

| 위험 | 지금 | 영향 |
|---|---|---|
| 백업 보존 1일 | RDS 생성 시 "연습용 1일", 바꾼 기록 없음 | 하루 넘게 늦게 발견한 데이터 손상은 복구 불가 |
| 시즌 와이프 되돌릴 수 없음 | `SeasonService`가 자정에 자동 삭제 | 와이프 버그 = 전원 데이터 손실 |
| 복원·롤백 훈련 안 함 | jar 롤백 코드는 있으나 실제로 깨진 jar로 확인 안 함 | 사고 때 처음 해 보게 됨 |
| 인프라가 콘솔 수작업 | SG, IAM, 경보, 버킷 모두 클릭으로 생성 | 재현·리뷰·복구 어려움, 포트폴리오로도 약함 |
| 스키마가 `ddl-auto=update` | ENUM 컬럼은 수동 `ALTER` 필요(Known Issues) | 배포 순서 실수로 기동 실패 |
| 비밀값이 파일 | `/etc/battle-royal/env` | 서버 재구축 시 손으로 다시 넣어야 함 |
| 배포 = 전원 접속 끊김 | 월드가 JVM 메모리에 있음 | 잦은 배포가 곧 플레이어 이탈 |
| 서버 안이 안 보임 | 경보는 EC2/RDS 바깥 지표뿐, 로그는 journal에만 | 틱 지연·접속 폭주를 모름 |
| 계정 존속 | 크레딧 방식 Free plan, $120 / 월 $25 안팎 | 크레딧 소진 또는 2027-04-03에 **계정이 닫힘**(유료 전환 전까지) |
| 도메인 1년 | 가비아 2026-10-03 구입 | 2027-10 갱신 놓치면 서비스 주소 상실 |

**P3 — 지표가 부를 때만 (C-트리거)**

아래 중 하나가 **실제로 관측되면** 두 대 구조를 설계한다. 그전에는 하지 않는다.

- 동시 접속이 한 JVM의 틱 예산을 위협(틱 p99가 계속 25ms 이상)
- CPU 크레딧이 매일 바닥(`br-ec2-cpu-credits` 경보가 반복)
- "배포마다 끊긴다"가 이탈의 주원인으로 확인됨(C11로 부족할 때)

그때의 설계는 이미 정해져 있다(`CLAUDE.md` §10): 방을 서버 한 대에 고정, Redis는 방→서버
디렉터리와 pub/sub에만, 20Hz 상태는 절대 Redis에 쓰지 않음, 두 대가 되면 ALB. 스케일업
(t4g.small/medium)이 먼저고, 스케일아웃은 그다음이다.

### 3.3 완료 기준

- 운영 DB를 **어제 이전 아무 시점으로** 되돌릴 수 있고, 실제로 해 봤다
- `terraform plan`이 "변경 없음"이다 — 콘솔과 코드가 같다
- 서버를 지우고 IaC + 배포 파이프라인만으로 다시 세울 수 있다(비밀값 포함)
- 틱 지연과 접속자 수가 대시보드에 있고, 이상하면 메일이 온다
- 배포가 예고 없이 사람을 끊지 않는다

## 4. 제품 개선

| 영역 | 문제 | 방향 |
|---|---|---|
| **콜드 스타트** | 지속형 PvP는 동시 접속자가 있어야 재미있다. 1~2명이면 3x3 월드에서 만나기 어렵다 | 군인(PvE)이 빈 시간을 채운다. 다음은 "정해진 시간대" 운영(저녁 시간 이벤트), 접속자 수를 첫 화면에 표시 |

| 게스트 → 계정 전환 | 게스트는 잃을 것도 쌓을 것도 없다 | 게스트 탈출 결과 화면에 "로그인하면 이게 창고로" |
| 공유 | 숟가락 들고 죽는 장면이 가장 웃기지만 밖으로 나갈 길이 없다 | 사망/탈출 화면 **공유 카드**(이미지 + 링크). 마케팅의 핵심 장치(§6) |
| 경제 | 돈이 쌓이기만 하는지 모자라는지 모른다 | 시즌 1 데이터로 판단(C9 지표 + DB 집계) |
| 공정성 | 크레이트 경유 복제(G5), 다계정 아이템 넘기기 | G5 수정, 계정 생성 속도 제한 |

## 7. 수익 모델(BM) — 선택지

전제: 이 게임의 운영비는 지금 월 $25 안팎이다. 수익의 첫 목표는 **서버비를 스스로 내는 것**이지
큰 매출이 아니다. 그리고 익스트랙션 장르에서 **창고·돈·장비를 파는 것은 바로 "페이 투 윈"
논란**이 된다(타르코프의 비싼 에디션이 큰 창고를 줘서 생긴 반발이 대표적). 지금 창고 확장과
가방을 게임 돈으로만 사게 한 설계가 이 함정을 피하고 있다. 지킨다.

| 모델 | 적합성 | 메모 |
|---|---|---|
| **꾸미기(외형)** | 높음 | 삼각형 색, 사망 카드 테두리, 닉네임 색. 승부에 영향 없음. 단 `CLAUDE.md` V1 범위는 "스킨 없음" — 결정 필요 |
| **시즌 패스(외형만)** | 중간 | 시즌제가 이미 있다. 보상이 외형·트로피 장식이면 공정성 유지 |
| 후원(서포터) | 높음, 작음 | "서버비 후원" + 닉네임 옆 표시. 가장 빨리 할 수 있고 논란 없음 |
| 광고 | 낮음 | 화면이 곧 지도라 넣을 자리가 없다. 넣는다면 거점 화면, 보상형만 |
| 창고·돈·장비 판매 | **하지 않음** | 페이 투 윈. 장르 특성상 치명적 |

결정 시점: 크레딧이 끝나기 전(§5, 2027 2~3월). 그 전에 §8을 먼저 풀어야 한다.
